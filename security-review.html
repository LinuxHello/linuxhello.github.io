Security, stability and performance review

A review of the architecture and the source code of Linux Hello as they stood on 22 November 2026: what is sound, what is not, and the reasoning behind each judgement.

This is not an independent audit. The review was done by an AI model, at the maintainer's request, on pre-alpha code that has had no release. It found real faults and they are listed here unfixed. Linux Hello must not be used to protect anything yet. How the review was done and what it did not cover

Summary

Linux Hello decides who gets into a computer, so the project asked for its own work to be examined before anyone relies on it. Much of the code was written by coding agents. This review read all of it with one question first: where can an attacker get in? Stability and performance came second.

The foundations are careful. Every caller is identified by the system bus, never by what a message claims. The PIN is never compared in software and never travels over D-Bus. The PAM module has no path that reports success after an error. Parsers reject what they do not understand. The services run in a tight sandbox, and the build pipeline pins every tool and action it uses.

The faults are mostly where separate parts meet. The most serious one lets a program running as the user capture the effect of a PIN that the user types at a real prompt, and replace the PIN with one it knows. Several others let any local user switch Linux Hello off for everyone, which sends sign-in back to the account password. None of the findings lets one user sign in as another without that user typing a PIN or presenting a finger or face.

The central promise is not built yet. The design says a fingerprint or face only satisfies a policy that the security chip (the TPM) checks, and is never a yes or no held by a program. Today it is a yes or no held by a program, and so is a correct PIN: nothing in the TPM is released by either. The project's own documents say this openly. It is the largest piece of work between this code and something that can be trusted.

How the review was done

The reviewer was Claude Fable 5.2, an AI model made by Anthropic, working through Claude Code on the maintainer's machine. Six separate review passes ran side by side, one for each trust boundary, and each read its files in full:

  1. the Agent's D-Bus interface and its state;
  2. PIN handling, the lockout, and the fingerprint and face methods;
  3. the policy engine;
  4. the PAM module;
  5. the TPM provider, the command-line tool and the Plasma parts;
  6. confinement, continuous integration and the release chain.

Each pass reported findings with file and line. The leading finding of every pass, and every finding rated medium or above that rests on code, was then checked again against the source before it was written down here. Where a pass built a small proof of concept outside the repositories, the finding says so. Nothing in any repository was changed by the review.

Reviewed: linux-hello at commit 05554d9 and linux-hello-architecture at commit 7640ab6, both of 22 November 2026, with the security profiles, scripts and workflows in them.

What the review did not do. Please read the findings with these limits in mind:

  • No finding was exploited against a running Agent on a real system bus. Proofs of concept drove the project's own library code, a fake bus, or a software TPM.
  • Nothing ran on a hardware TPM, under a real display manager, or on a distribution other than the developer's.
  • The virtual machine test scripts and the fuzzers were read, not run. Tests that open sockets could not run inside the review's sandbox.
  • GitHub settings that are hidden from anonymous callers, such as who may bypass a ruleset, were not seen.
  • An AI reviewer misses things and can be confidently wrong. A clean section below means "nothing found", not "nothing there". The outside audit the project plans before a stable release is still needed.

The architecture

Linux Hello has one central service, the Agent, which runs as its own unprivileged user and answers on the system bus. A small PAM module inside sudo, the login screen and the lock screen asks the Agent to check a person. The Agent runs the PIN, fingerprint and face methods and reports the outcome. A second service, the TPM provider, is the only code that links the TPM library. Passkeys in the browser, through a virtual security key, are designed and prototyped but are not in the code yet.

Decisions that hold up well

  • The PAM module is a thin client. It starts no thread, no child process and no async runtime inside sudo or the login screen, and speaks to the bus one message at a time. Code that runs inside another program's process is where crashes and privilege problems come from, so keeping it small is the right call. It links three small libraries.
  • The PIN has its own channel. It travels over a dedicated socket where the kernel names the sender, never as a D-Bus message that bus monitors or logs could capture.
  • The TPM decides. The Agent stretches the PIN with Argon2id and the TPM checks the result as a key's authorisation. No stored value on disk can be used to test a PIN guess without the TPM, with one exception listed as R-11.
  • The TPM library is kept out of the Agent. The process that parses requests from every local user does not contain the large C library that talks to the chip. A check in CI enforces it.
  • Unavailable is not the same as refused. When Linux Hello is broken the account password still works, and when it is working a wrong PIN ends the attempt. A security component that locks people out gets removed, so this trade is sensible. Its cost is stated in the open: with Linux Hello down, the password alone satisfies a rule that asks for two factors.
  • Decisions are written down. Twenty-eight decision records, a threat model and a list of numbered security properties exist, and they name their own open questions. Most of what this review found at the design level was already listed there.

Where the architecture is not yet what it says

  • Biometrics are a flag in a daemon today. A face match is the exit code of a child process and a fingerprint match is a text in a D-Bus signal. Either one becomes a "success" signal that the PAM module turns into a sign-in. No TPM command is involved. The project's first invariant forbids exactly this, and its documents record the question as open. Until it is answered, the fingerprint service and the face program are trusted completely for sign-in.
  • A correct PIN releases nothing. The TPM confirms the PIN and the provider returns one byte. No key hangs under the user's root key, there is no unlock state, and no policy session. That is honest for a sign-in prototype, but it means the property "unlock is a satisfied TPM policy, never a flag" has no code behind it.
  • The integrity of a PIN record rests on file permissions alone. The TPM provider accepts any key that loads under its primary key. Whoever can write a user's record file can install a key whose PIN they chose (R-19). Nothing inside the TPM ties a record to a user.
  • All users share one TPM lockout. The design answers this with a per-user counter in the Agent that stays below the TPM's limit. That answer is right in principle and does not hold in the code (R-02).
  • Howdy runs inside the Agent's boundary. The face program is Python code from another project, fed by a camera that anyone in front of the machine can reach before signing in. It runs as the Agent's user with the Agent's files (R-08).
  • Not designed against: a modified boot chain (the root key is not bound to boot measurements), an active interposer on the TPM's bus, and a keyboard grabber under X11. The threat model says so for the first and the third.

What is done well

Each point was checked in the code, not taken from the documentation.

Callers are identified by the bus

The Agent asks the bus daemon for each caller's user id and refuses when it cannot be read. No id is taken from a message. Calls that carry authority are tied to the one connection that opened the prompt, and bus connection names are never reused, so there is no process-id race.

Nothing is broadcast

Every signal is sent to a named recipient. A test on a real private bus has a bystander that must hear nothing. Refusals are word-for-word the same whether or not another user's prompt exists.

The PAM module cannot fail open

Success comes only from a "success" signal sent by the connection that owns the Agent's name. Every error, timeout, unknown value and panic maps to "unavailable" or "denied". The bus address is a constant, so sudo's environment cannot redirect it.

Memory-unsafe code is fenced in

unsafe appears in one 327-line file of the PAM module and in one generated bridge declaration. Each block was read and found sound: null checks, single frees, and the typed PIN wiped before its memory is released.

The PIN never crosses the TPM's wire in clear

Sessions with the TPM are salted and encrypt their parameters. A test records the traffic to a software TPM and searches it for the secret, with a control case that proves the recorder would see it.

Parsers are strict

Policy files reject unknown keys and values, and survived 30,000 levels of nesting in a probe. The PAM module's D-Bus decoder caps a message at 64 KiB before it allocates and has no loop that can spin. Prompt ids must be exactly 64 hexadecimal characters.

A user cannot loosen the administrator's rules

No input was found that makes a user's policy layer weaken an administrator's, across every field that exists today. A fuzz target checks this property, not merely the absence of a crash.

Reset is authorised properly

The destructive reset asks polkit about the caller's bus connection, needs the person's own password in the session in front, and deletes nothing if polkit is missing, slow or says no.

The sandbox is real

Both services run without capabilities, without a network, with a system-call filter, a closed device policy and no core dumps. The Agent checks its own AppArmor label before anything else and refuses to run unless it is enforced.

The build pipeline is disciplined

Every GitHub Action in every repository is pinned to a full commit hash. Tokens default to read-only. No workflow runs with secrets on code from a fork. Tools are fetched with pinned checksums. No dependency comes from git, and no advisory is ignored.

R-01A typed PIN can be taken by another program of the same user High

Attacker needs
A program running as the victim, and the victim typing their PIN once at any real prompt. The project's threat model names this attacker.
Where
crates/linuxhello-agent/src/methods/pin.rs:103-157, src/main.rs:123-125, src/methods/pin/enrol.rs:69-79 and 179-190

What happens. When a PIN arrives on the PIN socket, the Agent hands it to "whoever is waiting for this user". Only one waiter per user is kept, and a new one silently replaces the old one. A change of PIN is such a waiter, and any program of the user may start one.

So a malicious program starts a PIN change on a prompt of its own, just after the person's real prompt has started. The person types the PIN at the real prompt. The Agent delivers it to the malicious job as the "current PIN". The program then sends a new PIN of its choice, and the TPM accepts the change. The program now knows the user's PIN without ever having known the old one. If sudo uses Linux Hello, it can then become root.

Why it is rated high. The PIN is the root of the whole design, and the decision record for the bus states that a program of the same user cannot change the result of an authentication. A case for a lower rating exists: such a program could also show a fake prompt and ask for the PIN. The difference is that here the person does nothing wrong and sees nothing unusual, except that their sign-in fails once.

Related fault. When an older waiter ends, it removes the entry for the user even if a newer waiter has replaced it, so an honest retry can lose its PIN.

Fix. Tie a PIN to the prompt that announced it, deliver it only to the job started on that prompt, never replace one waiter with another, and let a waiter remove only its own entry.

R-02The per-user PIN lock does not stay below the TPM's limit Medium

Attacker needs
Any local account, acting on its own PIN.
Where
crates/linuxhello-agent/src/methods/pin.rs:199-219, src/pinlock.rs:142-144, src/main.rs:96-108, crates/linuxhello-tpm-provider/src/server.rs:99-112

A TPM counts wrong authorisations for the whole machine, so one user could lock everyone's PIN. The Agent is meant to prevent that with its own counter per user. Four things defeat it:

  • The check and the count are separate steps. The Agent asks "may this user try?", then runs the slow TPM check, then records a failure. A user may hold 64 prompts, each with its own job, so many wrong PINs are in flight before the first is counted. In a proof of concept with a limit of three, twenty checks reached the verifier.
  • A correct PIN clears the Agent's count but not the TPM's. By the TPM 2.0 specification the chip's counter only falls with time. A user who knows their own PIN can repeat "four wrong, one right" without ever being locked by the Agent while the chip's counter climbs. This follows from the specification and was not run.
  • The TPM's limit is read once, at start. The Agent's unit does not wait for the provider, so at boot the cap may never be applied.
  • An abandoned check still runs. The provider handles one request at a time. If the Agent gives up after 15 seconds, the provider still performs the check later, and the chip counts a failure that the Agent never records.

Fix. Count the attempt before asking the TPM and take it back on success. Read the chip's real counter before each attempt and refuse when little room is left. Start the Agent after the provider.

R-03Any local user can make the PAM module report "unavailable" Medium

Attacker needs
Any local account with a connection to the system bus.
Where
crates/pam-linuxhello/src/client/bus.rs:150-199, src/client/wire.rs:330-336

The module decodes every message it receives in full before it looks at who sent it. Its decoder knows only the few value types the Agent uses. The default policy of the system bus lets any user send a signal to any connection. So one signal carrying, say, a 32-bit signed integer makes the decoder fail, and the module gives up with "unavailable".

Sent in a loop, this switches Linux Hello off for every user's sudo, login and unlock, and the account password takes over. Sent just after a wrong PIN, it turns "denied" into "unavailable", so the same attempt goes on to the password prompt, which breaks the project's property P-32. This is a downgrade, not a bypass: the attacker still needs the password.

Confirmed against a fake bus through the module's public entry point. Delivery on a real bus daemon follows from the bus policy files and was not run.

Fix. Read the header first, drop messages that are not from the Agent or the bus without decoding their body, and keep "denied" once a PIN was refused.

R-04Remote sessions are not refused Medium

Attacker needs
A shell as the user without their password, for example through a stolen SSH key; a policy that allows face or fingerprint for sudo; the user sitting at the machine.
Where
crates/pam-linuxhello/src/entry.rs:272-278; no mention of a remote host, a seat or logind in the module or the Agent

Neither the PAM module nor the Agent asks whether the person is at this machine. sudo inside an SSH session therefore starts the methods on the local hardware. With face allowed, the person at the desk is matched without doing anything and the remote party becomes root. The fingerprint and face modules of other projects refuse remote sessions for this reason. The threat model does not discuss it.

Fix. Report "unavailable" when PAM names a remote host, and have the Agent require a local, active seat before it starts a sensor.

R-05One local user can exhaust the Agent's limits Medium

Attacker needs
Any local account.
Where
crates/linuxhello-agent/src/state.rs:61, src/bus.rs:236, 853, 961, 1028, src/pinkdf.rs:53-57, security/systemd/linuxhello-agent.service:48-49

A user may open 64 prompts and run one job on each. A sign-in job starts a thread for itself and one per method, and the face method starts a Python process. Every PIN check uses 64 MiB for Argon2. The service is limited to 128 tasks and 1 GiB. About fifteen PIN checks at once reach the memory limit, and 64 sign-ins pass the task limit.

The thread starts use a call that panics when the system refuses a thread, outside the code that catches panics. A reset job also waits up to two minutes for polkit and cannot be cancelled, while its prompt slot is freed at once.

The result is that Linux Hello stops for everyone and sign-in falls back to the password. The arithmetic comes from the code and the unit file; it was not run.

Fix. A small global limit on concurrent PIN work, a limit of running jobs per user far below 64, and thread starts that return an error.

R-06A release tag can skip the quality gate Medium

Attacker needs
Permission to push a tag. The maintainer and the coding agents' credentials have it.
Where
.github/workflows/release.yml:9-34; the repository has a branch ruleset and no tag ruleset

A release starts when a tag is pushed, and GitHub runs the workflow file from the tagged commit. The step that checks "this commit is on main and passed the gate" is part of that same file. A tag on a commit whose workflow has the step removed is still built, signed and published, and the command that SECURITY.md gives users to verify a download accepts it, because it checks only the workflow's path, the tag and the file's digest.

No release exists yet, so nothing has been affected.

Fix. A tag ruleset that lets only the maintainer create, move or delete release tags; a protected release environment that needs a reviewer; and a second verification command for users that checks the quality-gate attestation of the tagged commit.

R-07The checks a pull request must pass are defined by that pull request Medium

Attacker needs
Write access, or an agent that misbehaves under the maintainer's account.
Where
.github/workflows/ci.yml:35-52, 306-387, scripts/ci/verify-quality-gate.sh:29-43; ruleset: zero required approvals

The workflow, the list of gates and every gate script are read from the pull request itself. A change that edits them can turn every required check green, and after the merge the run on main signs a valid attestation with the same edited files. Nothing compares the list of gates that passed with a minimum kept elsewhere.

Merges need no approving review. The sign-off check looks for a line of text, not for a signature. The project's roles depend on the maintainer reading what is merged, which is a human control, not a technical one. The decision record on agent roles says part of this itself.

Fix. Run the gates from a protected reference as an organisation-level required workflow, have the verifier demand a minimum set of gates, and require a review from a code owner for changes to workflows, gate scripts and security profiles.

R-08Howdy runs with the Agent's user, files and TPM socket Medium, documented

Attacker needs
A flaw in Howdy's Python code or its image libraries that a camera picture can trigger. The camera is reachable before sign-in.
Where
security/apparmor/linuxhello-agent:63-81, crates/linuxhello-agent/src/methods/face.rs:64-105

The face program is started as a child of the Agent and inherits its AppArmor profile, because the kernel refused a narrower profile under the unit's settings. It can therefore write the PIN records and the lockout file and reach the TPM provider's socket. Code running there could clear a lockout, or replace a user's PIN record with one whose PIN it chose (see R-19), which is a sign-in bypass. The profile's own comment records this as a follow-up. The interpreter is also started without the options that stop it loading code from user site directories.

Fix. A separate unit, user and profile for the face program with no bus, no state directory and no TPM socket, as already planned.

R-09The Agent can open the TPM device although it never does Medium

Attacker needs
Code execution inside the Agent or its Howdy child.
Where
security/systemd/linuxhello.sysusers:4, security/systemd/linuxhello-agent.service:66, security/apparmor/linuxhello-agent:84

The Agent's user is in the group that owns the TPM device, its unit allows the device and its profile allows reading and writing it. Nothing in the Agent's source opens it; the Agent reaches the TPM only through the provider's socket. The three grants are left over from an earlier design and tests pin them in place.

They undo the separation the provider exists for. A compromised Agent could send the chip any command, not only the provider's five: create keys with attributes of its choice, drive the machine-wide lockout, or, where the owner password is empty as it usually is on Linux, clear the lockout.

Fix. Remove all three grants and invert the tests.

R-10A fault in one administrator file discards every administrator rule Medium, documented

Trigger
A typing mistake or wrong permissions in any file of /etc/linuxhello/policy.d/.
Where
crates/linuxhello-agent/src/policy/load.rs:96-101, 275-292

"Fail closed" here means "only the PIN", built from the built-in defaults. In a probe, an administrator policy asked for a twelve-character PIN, three attempts and two factors for sudo. Adding a second file with one misspelt key gave a six-character minimum, five attempts and one factor. Biometrics are switched off in that state, so it is not weaker in every respect, but an administrator who demanded two factors gets one.

For a fault in a user's layer the code keeps the administrator's rules; the same reasoning applies here.

Fix. Keep every administrator file that does parse, or the last good set, and never lower the number of factors.

R-11With PIN history on, former PINs can be guessed offline Medium; off by default

Attacker needs
A copy of a user's PIN record: a backup, an unencrypted disk, or the Agent's user.
Where
crates/linuxhello-agent/src/pinrecord.rs:64-76, src/methods/pin/tpm.rs:156-164

The current PIN cannot be guessed away from the machine, because the key it opens is wrapped by the TPM. The history of replaced PINs is different: each entry is an Argon2id hash with its salt, stored in the file. At about a tenth of a second per guess, all four-digit PINs take minutes and all six-digit PINs about 31 hours on one processor core. Former PINs are a good guide to the current one.

The default is no history, so a default installation is not affected. The decision record says guessing the history is as slow as guessing against the TPM's key material; that comparison does not hold.

Fix. Key the history with something only the TPM holds, usable only after the current PIN is proven, and correct the record.

R-12Security-relevant actions leave no audit record Medium

Where
crates/linuxhello-agent/src/audit.rs:59-73, src/bus.rs:1006-1069, tests/security_properties.rs:313-356

The Agent records refusals, policy changes and the PIN-only fallback. It writes nothing for a destructive reset, a first PIN, a PIN change, a fingerprint enrolment or deletion, or the outcome of a sign-in. The security policy promises that every unlock, PIN change and reset is audited. The test named for that promise checks only the five kinds of record that exist, so its name says more than it tests.

Related: refusals are written without a rate limit, one journal record per call, so any local user can flood the log.

R-13Lowering the attempt limit can refuse every user's PIN Medium, stability

Trigger
An administrator lowers pin.lockout_attempts, or the TPM cap applies on one start and not on the one before, while any user has that many saved failures.
Where
crates/linuxhello-agent/src/pinlock.rs:84-93, src/pinlock/service.rs:145-151

On start the Agent reads the saved counts. A count at or above the limit is treated as a damaged file, and a damaged file refuses every PIN of every user. Nothing recovers from it, not even a reset; someone must delete the file as root. It fails in the safe direction, but it turns a routine policy change into an outage. Confirmed with a proof of concept.

Fix. Treat such a count as a lockout for that one user.

Stability

What is solid. Each job and each method runs inside a guard that catches a panic and still reports a result. A sign-in attempt has an overall deadline. Prompts are cleaned up when their owner leaves the bus and again after five minutes of silence, on a clock that cannot run backwards. Record files are written to a temporary file, synced and renamed. A file that cannot be trusted is refused, never replaced by an empty one. The PAM module returns within about 2.3 seconds when the Agent is stopped or hung.

What is not.

  • Restart without pause. Both units restart one second after any failure, with the start limit switched off. A permanent fault, such as a profile that is not enforced or a TPM with an owner password, restarts the service every second for ever.
  • The provider does not heal. It creates its primary key once. If that handle becomes invalid, every later request fails until someone restarts the service. It has no watchdog and no resource limits.
  • One thread each. The provider and the PIN socket each serve one client at a time, so one slow client delays all (R-15).
  • Limits a single user can reach (R-05), and a lockout file that a policy change can invalidate (R-13).
  • An Agent restart during a sign-in is not noticed by the PAM module after the PIN was sent; it waits the full 30 seconds before giving up.
  • A slow Agent can delay the PIN question by up to about 12 seconds, because five calls each have their own two-second limit and there is no limit for the whole.
  • The release workflow has never run. Its build job does not install the TPM and PAM development packages that CI installs, so the first tag for those two parts will probably fail.

Performance

Nothing here is slow today on the developer's test setup. The concern is what happens on real hardware, which has not been tried.

ObservationReasoningSuggestion
Every PIN check makes the TPM generate an RSA-2048 keyTo prove the PIN, the provider asks the chip to create a throwaway child key with the RSA storage template. On a software TPM that takes milliseconds. On hardware chips RSA key generation is the slowest operation there is and commonly takes seconds, with wide variation. The client gives up after 15 seconds, which would look like "unavailable" and fall back to the password. This expectation was not measured.Prove the authorisation with a cheap object (a sealed blob or keyed hash) or an elliptic-curve key. This is the single most valuable performance change.
The primary key is regenerated at every start of the providerAnother RSA-2048 generation on the chip each boot; nothing is kept at a persistent handle.Persist the primary, and compare its name on start (this also addresses R-25).

Merging match patterns is quadratic: an administrator file of 1,000 KiB took 11 seconds per load. Only root can write such a file. Already listed as technical debt.Cache the merged policy and reload on change; cap the patterns per class.
Each PIN check uses 64 MiB for about a tenth of a secondThat is the intended cost of Argon2id and is reasonable. A PIN change runs it at least four times, more with history. The risk is many at once (R-05).Limit how many run together.

How far the tests can be trusted

The maintainer reviews behaviour, tests and test results, not Rust. The tests are therefore part of the security design, and they were reviewed as such.

Good practice found. Tests are named after the property they prove. Many run against real things: a private bus daemon, a software TPM with fresh state for each test, and a recorder on the TPM's traffic with a control case. CI fails, not skips, when the software TPM is missing. The confinement job really attempts the forbidden actions and expects a refusal.

Where a green result says less than it seems.

  • The tests for matching website names cannot fail. Six tests, among them the one for look-alike names such as evilbank.example, assert an answer that is also the answer when nothing matches. The matching code was deliberately broken in three ways in a scratch copy and all 124 policy tests still passed. The matching code itself was probed by hand and is correct.
  • Some names promise more than the test checks: the audit test (R-12) and the test for cleared PIN buffers (R-28).
  • Thirty-one tests are placeholders marked to be skipped, among them the central properties: a biometric match alone never releases a key, unlock is a TPM policy session, an unlock expires, and success is only for the user being authenticated. The property list says so. Some placeholders could be written today, and one is already covered by a real test elsewhere.
  • Nothing tests two things at once. No test runs two jobs for one user, concurrent wrong PINs, or a slow client. R-01, R-02 and R-15 live exactly there.
  • Rules about other users are tested by passing a user id to a function, not by a second user on a real bus, except in the confinement job.
  • The only unsafe code has no automated test. The PAM entry points are covered by review and by virtual machine scripts that are not part of the required checks.
  • The fuzz targets miss the faults found here. The policy target uses one administrator file, so R-14 is out of its reach. The PAM target fuzzes the decoder but not the message loop, where R-03 is. The TPM provider's decoder has no fuzz target.

This matters more for Linux Hello than for most projects. When code is written by agents and trusted through its tests, a test that cannot fail is a hole in the review, and a property whose test is a placeholder has had no review at all.

What to fix first

  1. Bind a PIN to its prompt (R-01). It is the one finding that gives an attacker a credential, and the change is small.
  2. Remove the Agent's access to the TPM device (R-09). Three lines of configuration and the tests that pin them.
  3. Make the PAM module ignore what it cannot read, and refuse remote sessions (R-03, R-04, R-16).
  4. Count PIN attempts before the TPM is asked, and bound concurrent work (R-02, R-05, R-13, R-15). One change to how attempts are reserved addresses most of it.
  5. Protect release tags and the gate definition (R-06, R-07) before the first release exists.
  6. Move Howdy out of the Agent's boundary and have the provider check the keys it loads (R-08, R-19).
  7. Repair the tests that cannot fail, and add tests with two actors for the PIN path.
  8. Measure a PIN check on a hardware TPM and replace the RSA key generation if it is slow.
  9. Decide how a fingerprint or face match is tied to the TPM. Until then, the invariant "biometrics are never a flag in a daemon" describes an intention, and the documentation should say so wherever it states the invariant.

The outside audit the project plans remains necessary. This review should make it cheaper by clearing what a careful reading can find.
