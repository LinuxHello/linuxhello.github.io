Passkeys and secrets for the Linux desktop

Unlock once with your face, fingerprint or PIN. Passkeys then work in browsers, native apps and Electron apps, rooted in a PIN and kept in the TPM or KeePassXC.

See the code Read the architecture

Pre-alpha. A first prototype can unlock sudo, but there are no releases and no external audit. Please do not rely on Linux Hello to protect anything. What exists today

What it does

Unlock once

Face, fingerprint or PIN unlocks the session. Passkeys then work everywhere through a virtual security key, without patching any browser.

The PIN is the root

Keys hang off a per-user TPM root key that your PIN authorises. Biometrics are a shortcut that satisfies a TPM policy, never a replacement for it.

Your choice of custody

A routing policy decides for each site or service whether its key is device-bound in the TPM or portable in KeePassXC.

Keys sign, never leave

Private keys stay inside the TPM or KeePassXC. Linux Hello asks them to sign; it never holds the key itself.

Fails closed

A broken policy denies everything except the PIN. The Agent refuses to start without its enforcing AppArmor profile.

KDE Plasma first

One prompt that shows which method is active, the same on the login screen, the lock screen and in the session.

How it works

Five layers sit between you and a site that asks for a passkey. Browsers see an ordinary USB security key, which is why they need no changes.

  1. UnlockPAM, with fprintd, Howdy and the PIN tried in parallel
  2. BrokerThe Agent: holds the unlock state, checks the policy and asks a provider to sign
  3. InterfacesCTAP2 over a virtual uhid security key for WebAuthn; the Secret Service for tokens
  4. RoutingPer relying party: device-bound or portable
  5. ProvidersTPM 2.0, KeePassXC, and a hardware security key as fallback

The full design is in the Arc42 sections, the C4 model and the decision records. The provider path is ADR-0005.

Where it stands

Built and tested

  • The Agent, the service at the centre: its state API on the system bus, the routing policy engine and the per-user policy layer, the fingerprint method through fprintd and the face method through Howdy, audit records, and the reset after a forgotten PIN
  • The PIN, stretched and checked by the TPM, with a lockout per user
  • The TPM provider, the one program that talks to the TPM, tested on a software TPM
  • The PAM module, which asks the Agent in sudo, at the login screen, at the lock screen and when a session is unlocked, and leaves your account password in charge when Linux Hello is not there
  • The command-line tool, which sets and changes the PIN and shows the state
  • The Plasma parts: the Agent Link, the Auth Prompt and Linux Hello's own login screen, tested in a desktop test VM
  • The Agent's confinement: D-Bus policy, systemd unit and AppArmor profile, tested in virtual machines

Proven in a prototype

  • A TPM-backed virtual authenticator, end to end with stock libfido2, Chromium and Firefox (spike 0094)
  • Keys bound to one relying party on a software TPM
  • A first prototype that unlocks sudo with a PIN kept by the TPM or with a fingerprint, made of the PAM module, the Agent's PIN check, the TPM provider and the command-line tool (how to try it and remove it)

Not built yet

  • Passkeys in the browser through the virtual security key, which exists only as the prototype on the left
  • The KeePassXC provider, which is a stub
  • The page in Plasma's System Settings
  • Tests on a hardware TPM
  • An independent security audit

The README of linux-hello is the current account of what is built. An AI-assisted review of the code in November 2026 is not an audit; which of its findings are fixed is listed on its page.

Built in the open, checked by machines

Attested quality gate

A commit passes only when formatting, Clippy, tests, cargo-deny, cargo-audit, the unsafe policy, fuzzing and docs all pass. CI then signs a Sigstore attestation for it.

Verifiable releases

Releases are built only from commits whose attestation verifies, with signed build provenance and a CycloneDX SBOM. Check a file with gh attestation verify.

Decisions on record

Every one-way decision, from the licence to the D-Bus names, needs an architecture decision record. Every security property has a test whose name states it.

How these work: ADR-0006 and SECURITY.md. What a review of the code found in November 2026, good and bad, and how far the fixes have come: the security review.

Contribute

Start with the backlog and CONTRIBUTING.md. Every commit is signed off under the Developer Certificate of Origin.

Much of the code is written with coding agents in fixed roles (ADR-0004), and a human decides and merges. The same rules and checks apply whoever wrote a line.

Report a vulnerability

Use the Security tab of linux-hello to report privately. Never open a public issue for a vulnerability. The security model and response times are in SECURITY.md.
